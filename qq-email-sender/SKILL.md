# QQ 邮箱发信

固定使用 QQ 邮箱 SMTP，纯文本 + 附件。发件账号固定为配置中的 QQ 邮箱，不做多账号切换。

脚本负责账号、授权码、联系人、SMTP 预检和发送；你负责判断收件人和内容是否合适，以及是否需要用户确认。

脚本是黑盒：尽量不要读源码，节省上下文；优先使用下面的命令和脚本的报错输出。
下面的 `scripts/qq_mail.py` 相对于技能目录；脚本报错里的命令会给出绝对路径，可直接复制。

## 命令

查联系人：

```bash
python scripts/qq_mail.py --contacts
```

保存或更新联系人（同名即更新）：

```bash
python scripts/qq_mail.py --set-contact "小号" --email test@qq.com --note "我的测试邮箱"
```

预览（不发信）：

```bash
python scripts/qq_mail.py --dry-run --to "a@b.com" --subject "..." --body "..."
```

长正文把 `--body` 换成 `--body-file`；附件加 `--attach "file.pdf"`，可以重复。

发送：

```bash
python scripts/qq_mail.py --to "a@b.com" --subject "..." --body "..." --yes
```

删除授权码：

```bash
python scripts/qq_mail.py --forget-auth
```

## 收件人判断

先看当前对话，不要默认查联系人。

直接使用地址的情况：

- 用户给了完整邮箱，例如 `发给 alice@company.com`。
- 用户说“还是发给刚才那个”，而本对话已经确认过那个地址。
- 用户说“发给小号”，而本对话已经确认小号对应的邮箱。

需要查联系人的情况：

- “发给公司账号”，但没有公司名或地址；联系人有“公司1、公司2”，列出来问发哪个。
- “发给小号”，但没有地址；联系人里有两个测试邮箱，问是哪个。
- “发给老王”，联系人有多个“老王”，问是哪个。
- 任何称呼、角色或备注对应多个邮箱，或你无法确定具体地址。

查过一次后，在当前对话里复用地址，不要每封邮件都重复查。多个候选时列出来问用户，不要猜。

## 默认流程

1. 收件人不明确时，先查联系人并确认。
2. 运行一次 `--dry-run`；脚本同时检查账号、授权码、SMTP 和邮件格式。
3. 出现 `[FAIL]` 时，把失败项和“善后”原样给用户，等用户完成后重跑。
   不要索要授权码，也不要替用户运行交互式 `--setup`。
4. 检查通过后判断风险：
   - 低风险、熟悉流程、用户已明确授权：可以加 `--yes` 直接发送。
   - 新收件人、敏感内容、实质变化、你不确定：把收件人、主题、附件摘要给用户，问“你看一下，要发送吗”。
5. 发送成功报告 `Message-ID`；失败按脚本的 `NEXT` 提示处理。

## 直接发还是先问

可以直接发：

- 用户明确说“直接发/不用预览”。
- 收件人已在本对话确认，或已保存为熟悉联系人。
- 内容低风险：测试邮件、简单文件、日常更新、自己的小号。
- 与上次已同意内容只有轻微措辞或附件更新。

先问：

- 新收件人、多个候选、外部陌生地址。
- 敏感信息、承诺、法律/财务/HR/医疗内容。
- 可能含隐私的附件、群发、实质内容变化。
- 你不确定是否合适。

邮件不能撤回；不确定时宁可问。

## 内容审查

- 收件人/抄送是否符合用户意图。
- 主题是否准确；即使用户说“随便”，也要选一个不误导的。
- 正文是否含敏感信息、不当语气或未经确认的承诺。
- 附件是否是正确文件，是否含隐私。
- 脚本只查格式，不判断语气和是否合适；这部分由你负责。

## 联系人写入

用户确认某个地址后，可以抛一个选择题：

```text
要把 alice@company.com 保存为“公司1”吗？
1. 保存，下次直接识别
2. 仅本次使用
```

选 1 才运行 `--set-contact`，带上用户认可的备注；选 2 不写配置。
不要静默修改联系人。

## 配置、授权码和未知错误

- 账号、显示名、联系人使用固定配置；授权码在系统钥匙串。
- 不要在聊天中索取或展示授权码。
- 如果 `--dry-run` 报配置缺失，把错误里的 `--setup` 命令交给用户，
  等用户在本机终端完成后，重跑刚才的 `--dry-run`。
- 如果出现 `E_UNKNOWN_*`，先按“原文”分析并与用户解决；
  修复被验证后，运行脚本提示的 `--record-fix` 命令记录善后方式。
  下次相同错误会读取配置并显示已记录的处理方式。
- 如果某个已知错误的内置善后不适用，也可以用 `--record-fix` 补充；
  下次会同时显示内置善后和“已记录的处理”。
- 如果脚本输出 `FEEDBACK` 或 `NEXT`，按其中提示询问用户是否反馈；不要自动发送。
